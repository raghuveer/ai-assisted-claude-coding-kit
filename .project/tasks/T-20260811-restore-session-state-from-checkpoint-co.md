## Intent

`kit-checkpoint.sh` and the `checkpoint` skill exist, and status is already derived from commits
rather than a hand-maintained file. What is missing is the other direction: **reconstructing
where you were** after a `/clear` or a new session.

This is the largest single cost lever the kit has. Session cost data from 2026-08-09 shows 79%
of spend at over 150k context and 97% from a session running eight-plus hours, and the recorded
diagnosis was that one context served four distinct tasks so every later request paid for all
the earlier ones. `/clear` between tasks is the fix, and it is only cheap if resuming is cheap.

## The change

Checkpoint commits carry a structured body — decisions taken, work remaining, approaches
already tried and rejected. A restore step reconstructs session state from those commits so a
fresh context reaches the same working position without re-reading the codebase.

Squash checkpoints before the PR so history stays bisectable. Keep push opt-in so CI is not
triggered on every checkpoint.

**"Approaches tried and rejected" is the load-bearing field.** Without it a restored session
cheerfully re-attempts what the previous one disproved, which costs more than the restore saves.

## Acceptance criteria

- [ ] After a `/clear`, a restored session reaches the same working state without re-reading the
      codebase — demonstrated on a real task, not asserted.
- [ ] The restore names what was already tried and rejected, and a restored session does not
      repeat one of them.
- [ ] Checkpoints squash cleanly before a PR; history remains bisectable.
- [ ] Push stays opt-in; a checkpoint does not trigger CI.
- [ ] A checkpoint with a malformed or missing body is reported at restore, not silently
      treated as an empty state.
